# ADR-006: «문구 회상»의 사진 보관과 Room 스키마 동결의 충돌

- 상태: **초안(제안) — 선택은 오너 [ASK].** 2026-11-03 · 코드 0
- 상위·관련: [ADR-002](ADR-002-on-device-ocr-rollout.md)(사진 비전송) · [ADR-004](ADR-004-reading-knowledge-base-architecture.md)(3단계 ⑧ `Migration(2,3)`) ·
  [ADR-005](ADR-005-internal-test-and-stage2-boundary.md) §2(스키마 동결)·§3(2단계 경계)·§6 ADR-004-4 · [STAGE2-PLAN 공통 DoD](../STAGE2-PLAN-2026-11.md)(:8-13)
- 명세: [PHRASE-RECALL-SPEC-2026-11](../PHRASE-RECALL-SPEC-2026-11.md)

## 맥락

오너 요청(2026-11-03 10:45): «떠오른 문구·단어 → 언제 어느 책에서 읽었는지 + **당시 촬영 사진**과 함께 핵심 문구 복기».

- 지금 앱은 사진을 기록과 연결해 보관하지 않는다. `Diary`에 사진 필드가 없고(`Entities.kt:57-64`, `2.json` diaries 6열), OCR 파이프라인은 비트맵을 추출 후 회수한다(`ReadingViewModel.kt:540-557`).
  카메라 원본은 `cacheDir` 임시 파일로만 남고(`OcrDiaryScreen.kt:110-118`, 미삭제 — ADR-002:30) 갤러리 사진은 일시 URI뿐이다(`OcrDiaryScreen.kt:153-165`).
- 사진을 «당시 사진»으로 다시 보여 주려면 **① 사진 파일을 앱 내부 저장소에 보관**하고 **② 어느 일기의 사진인지 연결**해야 한다.
  ②의 정석은 `diaries`에 경로 열을 두는 것 = **Room `version = 3` + `Migration(2,3)`**.

## 충돌

| 규칙 | 위치 | 내용 |
|------|------|------|
| 2단계 공통 DoD | `docs/STAGE2-PLAN-2026-11.md:10` | «**Room 스키마 변경 0** — `version = 2`·엔티티 필드 그대로» |
| 내부 테스트 스키마 동결 | ADR-005 §2(`ADR-005…md:39`) | «내부 테스트 기간 동안 Room 스키마 변경 금지 … 이 금지는 2단계 모든 PR의 DoD에 들어간다» |
| 마이그레이션 시점 | ADR-005 §3(`:54`)·§6 ADR-004-4(`:100`) | `Migration(2,3)`은 **3단계 ⑧**, `fallbackToDestructiveMigration` 제거와 **같은 PR** |
| 현재 빌더 | `AppDatabase.kt:38` | `fallbackToDestructiveMigration()` — 마이그레이션 없이 버전만 올리면 **기록 전체가 조용히 삭제** |

동결의 목적은 **테스터 기록 보호**다(ADR-005 §2 «테스터 기록이 조용히 전부 지워진다»). 따라서 위험의 크기는 «언제 바꾸나»에 달렸다:
첫 AAB 업로드 전이면 새 applicationId(`com.woodpeckerai.readingdiary`)로 깔린 기기는 오너의 디버그 설치뿐이고, 업로드 뒤면 테스터 ≤5명의 실제 기록이 걸린다.
첫 업로드 여부는 레포로 확인할 수 없다 — `AGENT_STATUS.json` `waiting_on`에 «U1~U8 사용자 손»(업로드 = U8)이 열려 있음만 확인(2026-11-03 09:35 기준).

## 선택지

### A. Room v3 + `Migration(2,3)` (정석)

`diaries.photoPath TEXT` nullable 1열 추가, `fallbackToDestructiveMigration` 제거, `3.json` 커밋, 마이그레이션 테스트 M1~M7(명세 §3.4). 사진 파일 이름은 UUID.

- **A-선행:** 첫 AAB 업로드 **전**에 머지. 2단계 DoD에 «ADR-006 예외 1건»을 적고 ADR-005 §2 동결 시작을 «첫 업로드 시점부터»로 명확히 한다.
- **A-후행:** 내부 테스트가 끝난 뒤(3단계 ⑧과 같은 묶음). 2단계 DoD는 그대로.

| 리스크 | A-선행 | A-후행 |
|--------|--------|--------|
| 마이그레이션 버그 → 기록 손실 | 오너 디버그 설치만 노출. 단, 파괴 폴백을 지우므로 **실패가 «조용한 삭제» 대신 «앱이 열리지 않음»**으로 바뀐다(되돌림 = 새 빌드) | 테스터 ≤5명 기록 노출. 같은 성질 |
| 일정 | 첫 업로드가 P3(3~4h)+검증만큼 늦어짐 | 업로드 영향 0, 사진 기능은 테스트 뒤 |
| 문서 정합 | ADR-005 §2·STAGE2-PLAN DoD **개정 필요**(같은 PR) | 개정 0 |
| 새 의존성 | `androidx.room:room-testing`(테스트 전용, Room 2.7.0 재사용) 1개 — 양쪽 같음 | 〃 |
| 편집 회귀(F6) | `saveDiary`가 `REPLACE` insert(`Daos.kt:63-64`) → 편집 시 `photoPath` 미전달이면 null로 덮임. M5 테스트로 고정 | 〃 |

### B. 스키마 변경 없이 파일 이름 규약으로 연결

`filesDir/diary_photos/{diaryId}-{createdAt}.jpg`. DB는 그대로(`version = 2`), 화면이 일기의 `id`·`createdAt`로 파일을 찾는다.

| 리스크 | 내용 |
|--------|------|
| **엉뚱한 사진 표시** | 파괴 마이그레이션·DB 재생성·일부 복원으로 id가 1부터 다시 매겨지면 남은 파일이 다른 일기에 붙을 수 있다(STAGE2-PLAN ③ 예시 책 표식과 같은 문제, `AppDatabase.kt:54-58`) → `createdAt`을 이름에 넣어 2중 대조로 낮추지만 0은 아님. **사용자가 날짜를 고치면**(`OcrDiaryScreen.kt:209-226`) 이름을 바꿔야 한다 |
| 고아 파일 | CASCADE가 파일을 모른다 → 삭제 연동 + 시작 시 sweep 필수(A도 같음, B는 판정이 더 약함) |
| 이중 정본 | 연결 정보가 DB 밖에 있어 내보내기·마이그레이션·3단계 ⑧ 때 **어차피 열로 옮기는 2차 작업**이 생긴다 |
| 장점 | 2단계 DoD·동결과 충돌 0, 첫 업로드 일정 영향 최소, 되돌림 = 폴더 삭제 |

### C. 미룸 — 2단계에는 사진 없는 회상만

명세 P1(검색·필터·카드, 스키마 0)만 2단계에. 사진 보관(P2~P4)은 A-후행과 같은 시점.

| 리스크 | 내용 |
|--------|------|
| 요구 미충족 | 원문의 «당시 촬영 사진»이 빠진다. 부제 후보 2·3을 쓸 수 없다 |
| **되돌릴 수 없는 손실** | 미루는 동안 찍은 사진은 보관되지 않아 **나중에 기능이 생겨도 그 기록에는 사진을 붙일 수 없다** |
| 장점 | 위험 0, 계획 변경 0 |

## 공통 조건(어느 선택지든)

1. 사진 폴더 `diary_photos/`는 **클라우드 백업에서 제외**(`backup_rules.xml`, `data_extraction_rules.xml` `<cloud-backup>`) — 안 하면 사진이 Google 드라이브로 나가 ADR-002와 충돌하고, 자동 백업 한도(앱당 25MB)를 넘겨 **일기 DB 백업까지 멈출 수 있다.** 테스트로 고정.
2. 외부 전송 경로 추가 0(`GeminiKeyPolicyTest` 불변). 보관 사진을 자동으로 정밀 분석·공유하지 않는다.
3. 처리방침 `privacy-policy.html:41`, 데이터 안전 표(INTERNAL-TEST §5)를 **사진 보관 PR과 같은 PR**에서 고친다.
4. 카메라 임시 파일은 보관 복사 후 삭제(ADR-002:30 해소).

## 결정

**[ASK] 오너 선택:** A-선행 / A-후행 / B / C.

에이전트 의견(참고, 결정 아님): 원문 요구와 «손실은 되돌릴 수 없다» 원칙을 함께 보면 **A-선행**이 가장 정직하다 — 위험이 가장 작은 시점(테스터 기록 0)에 정석 경로를 밟는다. 첫 업로드를 늦출 수 없다면 B보다 **A-후행 + P1 먼저**를 권한다(B의 이중 정본은 3단계에서 다시 갚아야 하는 빚).

**부속 질문(막지 않음, 기본값으로 진행 가능):**
- 기기 간 직접 이전(device-transfer)에 사진 포함? 기본값 **포함**(케이블·근거리 이전은 클라우드가 아니다). 원하지 않으면 `noBackupFilesDir`로 바꾸면 둘 다 제외.
- 저장 화면 «이 사진을 기록과 함께 보관» 기본값? 기본값 **켬**(요청 기능이므로) + 한 번 끄면 그 값을 기억.

## 재검토 조건

- 첫 AAB 업로드가 이미 끝났다면 A-선행은 자동으로 A-후행이 된다.
- 내부 테스터가 사진 보관으로 저장 공간 문제를 보고하면 → 해상도(긴 변 2048) 재검토.
- 일기 1건에 사진 여러 장 요구가 생기면 → 열 대신 `diary_photos` 테이블(F6: `saveDiary`를 `@Update`로 바꾸는 선행 작업 필요 — `REPLACE`의 삭제 단계가 `ON DELETE CASCADE`로 사진 행을 지운다).
