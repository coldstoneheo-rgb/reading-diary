# ADR-001: Gemini API 키 배포 정책과 이미지 텍스트 추출 비용 모델

- 상태: **채택(1단계 시행)** · 2026-09-05
- 결정자: 프로젝트 오너
- 관련 코드: `app/build.gradle.kts`(secrets 플러그인), `data/api/GeminiApiClient.kt`, `data/SecureKeyManager.kt`, `ui/screens/OcrDiaryScreen.kt`

## 배경

독서 다이어리의 "밑줄 구절 추출"은 촬영한 책 페이지 이미지를 Gemini(vision)에 보내 텍스트를 받아온다.
현재 구조에는 두 가지 문제가 있다.

1. **키가 앱 파일에 박힌다.** secrets 플러그인이 `.env`의 `GEMINI_API_KEY`를 `BuildConfig` 상수로 굽는다.
   APK를 뜯으면 누구나 키를 꺼내 쓸 수 있고, 그 요금은 키 주인에게 청구된다. 앱 서명·난독화로는 막을 수 없다.
2. **호출마다 돈이 든다.** Gemini 이미지 분석은 건당 과금이다. 독서 다이어리는 사용자가 돈을 낼 만한 카테고리가 아니므로
   (오너 판단), 무료 앱이 유료 API를 무제한으로 호출하는 구조는 지속 불가능하다.

## 결정

### 원칙
- **Gemini 키(또는 어떤 유료 API 키도)를 앱 바이너리에 포함하지 않는다.** 빌드 시점에 `BuildConfig`로 굽지 않으며,
  코드에 상수로 두지 않는다. 키는 (a) 사용자 기기 안의 암호화 저장소, 또는 (b) 우리가 운영하는 서버에만 존재한다.
- **기본 경로는 무료·온디바이스여야 한다.** 유료 API는 선택 기능으로만 얹는다.

### 1단계 (지금, 이 ADR과 함께 시행)
- secrets 플러그인 `ignoreList`에 `GEMINI_API_KEY`를 추가해 `BuildConfig` 생성을 막는다. `.env.example`에서도 항목을 제거한다.
- `GeminiApiClient`는 `SecureKeyManager`(EncryptedSharedPreferences)에서 키를 읽는다. 키가 없으면 지금처럼 예시 문장 폴백.
  네이버 키와 같은 저장 방식이며, 현재는 키를 넣는 화면이 없으므로 **사실상 Gemini 경로는 꺼진 상태**가 된다.
- 불변식을 테스트로 고정한다(`GeminiKeyPolicyTest`): `BuildConfig`에 `GEMINI_API_KEY` 필드가 없고, 키 미등록 상태의
  추출 호출은 네트워크 없이 시뮬레이션 문장을 돌려준다.
- Gemini 요청은 URL 쿼리(`?key=`) 대신 `x-goog-api-key` 헤더로 키를 보낸다(로그·프록시에 남지 않게).

### 2단계 (다음 PR들)
- **온디바이스 텍스트 인식 도입** — ML Kit Text Recognition v2(한국어 스크립트 모델)로 크롭한 영역의 텍스트를 추출한다.
  키·서버·요금이 없고 오프라인에서 동작한다. 앱 소개(`metadata.json`)의 "온디바이스 카메라 OCR" 문구와도 맞는다.
  이것이 모든 사용자의 기본 경로가 된다.
- **설정 화면에 "내 Gemini 키" 입력란** — 정밀 분석을 원하는 소수 사용자가 자기 키(Google AI Studio 무료 등급 가능)를 등록해 쓰는
  BYO(Bring Your Own) 방식. 운영 비용 0, 키는 사용자 기기 밖으로 나가지 않는다.

## 검토한 대안과 비교

| 안 | 운영 비용 | 키 안전 | 사용자 마찰 | 구현 부담 | 판단 |
|----|-----------|---------|-------------|-----------|------|
| A. 온디바이스 OCR(ML Kit) | 0 | 키 없음 | 없음 | 중(의존성 + 크롭 흐름 연결) | **기본 경로로 채택** |
| B. 서버 프록시 + 무료 한도(예: 기기당 월 20건) | 서버 + API 요금. MAU 1천·월 20건이면 대략 월 수만 원대 | 서버에만 존재 | 없음(한도 초과 시 안내) | 높음(백엔드, App Check/남용 방지, 기기 식별) | 수요가 확인되면 재검토 |
| C. 보상형 광고 후 분석 | B와 동일 + 광고 SDK | B와 동일(서버 필수) | 광고 시청 | B + AdMob 연동 | 건당 광고 수익(수 원~수십 원)이 API 원가(1원 안팎)보다 크므로 수익성은 있음. 그러나 B의 서버·남용 방지 부담을 그대로 상속하고 독서 기록 UX를 해침. 보류 |
| D. BYO 키(사용자 본인 키) | 0 | 기기 암호화 저장 | 높음(키 발급 절차) | 낮음(SecureKeyManager 재사용 + 설정 UI) | **선택 기능으로 채택** |
| E. 유료 구독 | 0(수익) | 서버 필수 | 결제 | 높음(결제 + 서버) | 오너 판단상 지불 의사 낮음. 보류 |

핵심 근거:
- B/C/E는 모두 **서버가 있어야** 키를 숨길 수 있다. 서버가 없는 현 상태에서 실행 가능한 안은 A와 D뿐이다.
- 책 본문은 인쇄 활자라 온디바이스 OCR 정확도가 높다. LLM이 더 잘하는 것은 "밑줄 친 부분만 골라내기"인데, 이미 사용자가
  영역을 크롭하는 흐름이 있어 그 이점이 크지 않다.
- 광고(C)는 건당 수익이 원가를 넘기는 하지만, 그 전제인 서버(B)를 먼저 세워야 하고 독서 기록이라는 조용한 사용 경험에
  광고를 끼워 넣는 비용이 크다. 서버를 세울 만큼 수요가 확인된 뒤에 B와 함께 재검토한다.

## 결과 및 영향

- 이 ADR 시행 직후: 앱은 키를 포함하지 않는다. 밑줄 추출은 키가 없으므로 예시 문장 폴백만 동작한다(2단계 A 전까지의 과도기).
  이 상태의 안내 문구는 "다음 업데이트에서 지원 예정"으로 두고, 존재하지 않는 등록 절차를 안내하지 않는다.
- `.env`에 `GEMINI_API_KEY`가 있어도 빌드에 들어가지 않는다. AI Studio에서 실행할 때 주입되던 경로도 끊긴다(의도된 결과).
  `metadata.json`의 `MAJOR_CAPABILITY_SERVER_SIDE_GEMINI_API`와 설명 문구는 AI Studio 매니페스트라 의도적으로 유지하며,
  2단계 A 이후 실제 동작에 맞춰 재검토한다.
- 서버를 두지 않으므로 사용자 데이터(사진)는 사용자가 직접 키를 등록한 경우를 제외하면 기기 밖으로 나가지 않는다.
- **기기 저장소의 한계(정직하게 적어 둠):** `SecureKeyManager`는 EncryptedSharedPreferences 생성이 실패하면 같은 파일명의
  **평문** SharedPreferences로 폴백한다. 또 `allowBackup="true"`에 백업 제외 규칙이 비어 있어 prefs가 클라우드 백업에 포함된다.
  현재는 Gemini 키를 저장하는 호출자가 없어 실제 노출은 없지만, 2단계 D(설정 UI)를 붙이기 **전에** 다음을 먼저 한다:
  (a) `backup_rules.xml`/`data_extraction_rules.xml`에서 `secure_user_prefs` 제외, (b) 폴백 상태에서는 Gemini 키 저장을 거부.
- **키 회전 권고:** 과거 실제 키가 든 `.env`로 빌드한 APK가 기기나 AI Studio에 남아 있을 수 있다. 코드에서 키를 빼도 그 키는
  안전해지지 않으므로, 그런 키가 있었다면 Google AI Studio에서 폐기·재발급한다.
- 2단계 착수 시 최우선 확인: `GeminiApiClient`의 모델 ID(`gemini-3.5-flash`)가 실제로 존재하는지. 틀리면 BYO 키를 등록해도
  항상 404 → 폴백이라 D 시나리오가 성립하지 않는다.

## 재검토 조건

- 온디바이스 OCR의 한국어 인식 품질이 실사용에서 불만족스러울 때 → B(서버 프록시 + 한도)를 다시 검토.
- 월간 활성 사용자가 유의미하게 늘어 서버 운영 비용을 정당화할 수준이 될 때.
