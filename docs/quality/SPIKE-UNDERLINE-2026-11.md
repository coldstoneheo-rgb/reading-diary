## 4. 제품화 — «미리 선택 + 줄 고르기 UI(D)», PR 4개 순서

1. **상자를 돌려받기**: `OcrOutcome.Text`에 줄·어절 상자(자른 비트맵 좌표)를 싣는다 — `MlKitTextExtractor`가 이미 받는 `TextBlock.lines[].elements[].boundingBox`. 화면 변화 0, 단위 테스트(가짜 추출기). + 디버그 빌드 한정 «상자 덤프»(기준 자료 `boxes/mlkit-…/`로 옮길 TSV) — **기기 ML Kit 상자로 같은 자료를 다시 재는 길**.
2. **검출 연결(미리 선택만)**: 인식 뒤 같은 비트맵으로 `UnderlineDetector` → 고른 어절 표시값. 줄마다 `lineSlope(어절 상자)`를 `slopes`로 넘긴다(없으면 정밀도 90.5% · 비침 4 — §5). 결과 글은 지금처럼 전부(동작 변화 0) — 기기에서 상자 덤프 + 미리 선택 결과를 기준 자료로 재 문턱을 고정.
3. **줄 고르기 UI(D)**: 결과 화면에 인식된 줄 목록(미리 선택된 어절 강조) → 눌러 넣고 빼기 → 고른 글만 편집창. 스크린샷 골든 + 화면 테스트. 문구를 «밑줄 인식»으로 되돌리는 것은 이 PR(LC DEC §4-1).
4. **형광펜(C) 켜기**: 형광펜 사진이 기준 자료에 3장 이상 들어온 뒤, 같은 측정으로 문턱 확인 후.

## 5. 남은 위험

- **상자 의존:** §1 수치는 Tesseract 상자 기준(기기 ML Kit 상자 수치는 §1-0, 2026-11-12). ML Kit 상자는 줄 기울기를 따라 회전된 사각형(코너 점 4개)을 준다 — 띠를 줄 기울기에 맞춰 돌리는 것(검출기 입력에 기울기 1개)은 2026-11-14 K2로 넣었다(§1-0-2).
- **옅은 물결 밑줄:** 2026-11-25 두 단계 문턱 뒤 3번 42.5% · 9번 46.7%(놓침 47 남음 — §1-0-5). 이전 기록: 보정 뒤(0.28Δ · K1a+K2)에도 3·9번이 35% 안팎으로 놓친다(5번은 95.2%로 회복). 문턱을 더 내리면 본문 밖 오검출이 14~24로 는다(§1-0-2).
- **해상도:** 문턱 · 띠 값은 원본 해상도 사진으로 골랐는데 앱은 1/2 해상도에서 부른다(§1-0-3 — 보정 전 재현율 70.8% → 64.2%, 줄 높이 보정 뒤 69.4%). 제품 기준 수치는 앱 해상도 · 앱 어절 판정 표다(§1-0-5 — 205/3/66 · 98.6% · 75.6%, 직전 §1-0-4 190/5/81). 보정(`smoothMinHeight = 60`)은 **고정 픽셀 문턱**이라 촬영 거리 · 판형에 걸린다 — 더 가까이 찍거나 큰 판형이면 앱 본문 줄이 H 60을 넘어 다시 평균되고 그 줄은 보정 전 수준으로 돌아간다(앱 쪽 여유 약 5px). 값은 11장 · 한 권 · 연필 표본에서 골랐다(과적합).
- **기울기 없이 부르면 정밀도가 무너진다:** 기본 띠(K1a)는 `detect(..., slopes)`에 줄 기울기를 넘긴다는 전제로 고른 값이다. 기울기 없이(`slopes = null`) 부르면 11장에서 정밀도 90.5% · 비침 오검출 4(규칙 «비침 ≤ 2» 위반)다. 앱 연결(§4 PR 2)은 반드시 `lineSlope`로 기울기를 넘긴다.
- **정답 미확정:** 2·4·9·10번 밑줄 범위는 2026-11-13 사용자 확인지로 확정(§1-0-2). 10번 2~3째 줄 2구간만 사용자 답 없이 LC가 사진으로 확인한 값이다. 나머지 장은 여전히 워커 초안.
- **표본 편향:** 11장 모두 한 권·연필. 형광펜·볼펜·다른 판형 0장 → 형광펜(C)은 실사진 0장.
- **자필 메모:** 갤럭시 [T]도 53.8% — 기기 안 엔진의 상한이 낮다. 사용자 기대(«미리 뽑고 고친다»)대로 편집 UI가 핵심.
